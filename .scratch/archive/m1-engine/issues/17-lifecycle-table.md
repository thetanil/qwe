# 17: The job lifecycle table and its four test layers

Status: resolved
Category: enhancement
Type: task
Blocked by: 08

## What

Build the job lifecycle of ADR-0010 as a pure module, test-first, **without wiring it into the engine** (that is ticket 18). The module is data plus one function. Given a (state, event) pair, it returns the cell: its kind (transition, ignore or impossible), the next state, the reason and the actions. It does no I/O, and it has no dependencies beyond libc.

The states, events, cell kinds and rules are those in ADR-0010, which is the contract. Where this ticket and the ADR disagree, the ADR wins.

## Acceptance criteria

- [x] **Layer 1 (completeness):** every (state, event) cell is exactly one of transition, ignore or impossible. None is left unset, and every ignore cell carries a non-empty justification. `unit: src/kernel/lifecycle_test.c::every_cell_classified`
- [x] **Layer 2 (rules over all cells):** each rule is one assertion over all cells. `unit: src/kernel/lifecycle_test.c::rules_hold_in_every_cell`
  - A final state has no transitions.
  - An ignore cell never changes the state and has no actions.
  - A SIGKILL action only leaves a state in which SIGTERM has already been sent.
  - The grace timer is armed only when leaving a state with no teardown in progress.
  - From every live state, `cancel` leads only to `settling-cancel-requested-*` or `skipped`.
  - Every transition into `failed`, `skipped` or `cancelled` sets a reason.
  - `leader-exit-fail` records the event's reason unchanged.
- [x] **Layer 3 (exhaustive exploration):** a breadth-first search from `pending`, driven by the event model, covers every state and event. `unit: src/kernel/lifecycle_test.c::impossible_cells_unreachable`, `unit: src/kernel/lifecycle_test.c::every_possible_cell_reachable`
  - No event sequence the model allows reaches an impossible cell.
  - Every transition and ignore cell is reached.
- [x] **Event model:** it lives in its own file and states which events can occur in which state. It is written independently of the table, and it never reads the table. `unit: src/kernel/lifecycle_model.c` (exercised by the two layer-3 tests)
- [x] **Layer 4 (scenarios):** named event sequences produce the expected sequence of (state, event, next state, reason) records. `unit: src/kernel/lifecycle_test.c::scenario_*`
  - A clean run of two steps ends `success`.
  - A step fails with and without `continue-on-error`.
  - A step timeout, then `grace-expired`, then `group-empty`.
  - A step timeout, then a job timeout (the job becomes `cancelled`/`timeout`, and grace is not re-armed).
  - A job timeout, then an operator cancel (the reason becomes `cancel-requested`).
  - Stragglers outlive a successful leader.
  - `start-failed` gives `engine-error`.
  - `needs-failed` and a cancel in `pending` or `ready` give `skipped` with the right reason.
- [x] Looking up an impossible cell aborts. `unit: src/kernel/lifecycle_test.c::impossible_cell_aborts` (by fork, as in `job_state_test`)

## Agent Brief

**Category:** enhancement
**Summary:** Implement ADR-0010's job lifecycle as a pure, table-driven module with four layers of tests. Do not wire it into the engine.

**Current behavior:**
Job and step state is spread across flags in the workflow event loop, and the job state machine covers only the job-level states. Nothing enumerates (state, event) combinations.

**Desired behavior:**
A pure module holds a flat table of about 21 states × 13 events (see ADR-0010) and one lookup function. Every cell is decided, and the tests prove three things: the table decides every case, it obeys the rules, and real inputs can never reach a fail-stop.

**Key interfaces:**
- Three enums: the lifecycle states, the events and the action kinds, named as in ADR-0010.
- A lookup `(state, event) → cell`. A cell holds its kind, the next state, the reason (or none) and a small fixed array of actions.
  - An impossible cell aborts inside the lookup.
  - `leader-exit-fail`'s reason is passed in as payload, not given by the table.
- The event model: `(state) → set of events that can occur`. It is a separate compilation unit that only the tests link.
- The action kinds are at least spawn step, SIGTERM group, arm grace timer, SIGKILL group, record step outcome, record job outcome and end job.

**Acceptance criteria:** the checklist in this ticket's Acceptance criteria section.

**Out of scope:**
- Any change to the workflow event loop, `result.json`, the lifecycle trace or the CLI (ticket 18).
- The subreaper and actually observing group-empty (ticket 19). The table does include the `group-empty` event and the `settling-*` states.
- cgroups.

**History:** this ticket began as "consolidate the job and step lifecycle", filed from a review of tickets 06–08 on 2026-09-19. Grilling produced ADR-0010 and split the work into tickets 17–20. The review's findings, as filed:



Already fixed while this ticket was being filed (not committed yet):

- **The e2e harness never compared `expected/RUN/*` goldens under Bazel.** `run_case.sh` listed goldens with `find . -type f`, and Bazel stages them as symlinks, so it found nothing. Only exit, stdout, stderr and `check.sh` were ever checked. Now it uses `find -L`, and `harness_selftest_run_golden` guards against regression. The `result.json` goldens of tickets 06–08 had never actually been checked.
- **An operator cancel started jobs that were `ready` and waiting for a `max-parallel` slot.** They ended `cancelled`, with times and a log, instead of `skipped`. `operator_cancel` was failing and only passed because of the harness bug. The state machine now has `ready → skipped` (reason `cancel-requested`), and design §7.2 has been amended to match.

Still open:

1. **`terminating` is a state only on paper** (design §7.1: "Teardown in progress"). A job stays `running` through its teardown, and `job_finish` moves it `terminating → cancelled` at once. `sched.c` counts `terminating` as live, but no job is ever in that state long enough to be counted.
2. **The grace period is cut short** (spec §3: "SIGTERM …, a 10-second grace period, then SIGKILL"). `step_reap` SIGKILLs the whole group as soon as its leader exits, so a child that traps SIGTERM loses the rest of its grace period.
3. **Step outcomes and reasons are string literals** spread across branches. `t == TRIG_CANCEL ? "cancel-requested" : "timeout"` appears in both `step_record` and `job_finish`, and `failed` together with `torn` encodes the job outcome implicitly. Job states are an enum, but step states are not.
4. **The job-start failure path** (the log cannot be opened) invents a reason, `internal`, that spec §2 does not list, and leaks the job's ring and timer.
5. **The tests that should prove teardown are weak:**
   - `grace_then_sigkill` only proves that the shell died; an immediate SIGKILL would pass it too.
   - `operator_cancel` and `parallel_cancel` send their signal at a fixed 0.7 s, which ticket 08 asks to avoid. Starting the cancel when a marker file appears would remove the timing dependence.
6. **`workflow.c` does too much** (about 800 lines): loading jobs and refusing unimplemented keys, the event loop, teardown, scheduler glue and building the result. The lifecycle could move into its own module, and `load_jobs` into another.


### Resolution

`src/kernel/lifecycle.{h,c}` (table + lookup), `lifecycle_model.{h,c}` (event model, linked only by the test), `lifecycle_test.c` (layers 1–4, abort by fork). Not wired into the engine; `job_state` is untouched until ticket 18.

Decisions worth knowing:
- `next-step` carries `coe` as payload (a `coe_by_payload` flag on the cell picks state or state+1), like `leader-exit-fail`'s reason; the event count stays 13. ADR-0010 notes this.
- A cancel in `between-steps` goes to `cancelled`, not `settling-cancel-requested-*`: no step is live, so there is nothing to settle. The layer-2 cancel rule allows exactly that one exception. ADR-0010 notes this too.
- `start-failed` is decided in `step-running`/`-coe` (spawn fails after the state is entered) and in `between-steps` (job start fails).
- Reasons are kinds: fixed, `FROM_EVENT` (leader-exit-fail from a running state only) and `CARRIED` (the settling-fail → failed cell, so the failing step's reason survives the wait).
- After a step timeout, both leader exits record `timeout`: a timed-out step failed whatever its leader said.
- A cancel or job timeout arriving in a `settling-*` state changes the job's reason but does not re-record the step.
- A cancel is broadcast to every job, so final states carry a justified ignore cell for it.
