# 21: Job and step ids follow a naming rule

Status: resolved
Category: bug
Type: task
Blocked by: none

## What

The schema accepts any string as a job id, and the engine builds the job's log path as `<run-dir>/<job-id>.log` with the id pasted in unchanged. Checked on 2026-09-19:

| Job id | Result |
|---|---|
| `../../../escaped` | `escaped.log` is written next to the workflow, outside the run directory. More `../` reaches any writable path, and an existing `*.log` there is truncated. |
| `a/b` | the job fails to start: "cannot open the log of job a/b" |
| `""` | a hidden file, `.log`, is written |

This is not a privilege boundary, because a workflow author can already run anything through `run:`. It is a correctness bug, and ids are about to be used in two more places that need them to be plain names:
- **The lifecycle trace (ticket 18):** each line is space-separated, so a space or newline in an id breaks it.
- **Templating (ticket 11):** references like `needs.<id>.outputs.x` only parse if ids are identifiers.

**The rule,** which is GitHub Actions' rule: a job id or a step `id:` matches `[A-Za-z_][A-Za-z0-9_-]*` and is at most 64 characters. It is checked during validation, so `qwe validate` and `qwe run` both reject a bad id before anything runs.

ADR-0009 removed `pattern` and `patternProperties` from the strict metaschema until a regex engine exists. So this is a check in the validator, next to the duplicate step id check, not a schema keyword.

## Acceptance criteria

- [x] A job id with `/`, `..`, a space, or a leading digit or `-`, and an empty id, are each a validation error. The error names the id and points at the key as `file:line:col`, and qwe exits 2. `e2e: tests/e2e/validate_bad_job_id/`
- [x] A step `id:` that breaks the rule is a validation error pointing at the value. `e2e: tests/e2e/validate_bad_step_id/`
- [x] An id of 64 characters is accepted, and one of 65 is rejected. `unit: src/kernel/validate_test.c::id_length_limit` (or an e2e case if the check is only reachable through the binary)
- [x] Every bad id in a workflow is reported, not only the first, consistent with the other validation errors. `e2e: tests/e2e/validate_bad_job_id/`
- [x] `qwe run` on a workflow with a bad id creates no run directory and writes no log. `e2e: tests/e2e/run_refuses_bad_id/`
- [x] The rule is stated in the M1 spec's "Workflow YAML" section and in design §14.

## Agent Brief

**Category:** bug
**Summary:** Reject job and step ids that are not `[A-Za-z_][A-Za-z0-9_-]*` (up to 64 characters) at validation, because ids become file names, trace fields and template references.

**Current behavior:**
Any string is accepted as a job id or step id. A job id is used as part of a file path without any check, so `../x` escapes the run directory, `a/b` fails the job at start, and `""` writes a hidden `.log`.

**Desired behavior:**
Validation rejects a bad id with a `file:line:col` error, just as it does a duplicate step id. Nothing runs and no run directory is created. Valid workflows behave exactly as before.

**Key interfaces:**
- The validator's post-schema checks, where duplicate step ids and the `needs:` graph are checked, gain an id check for every key under `jobs` and every step `id:`.
- Error positions come from the transcoder's position table: the key position for a job id, and the value position for a step `id:`.

**Acceptance criteria:** the checklist in this ticket's Acceptance criteria section.

**Out of scope:**
- A configurable runs directory (`--runs-dir`). That is a separate feature, and ids must be safe wherever the runs directory is.
- A naming rule for other names (env keys, secret names, output keys). They are dealt with in the tickets that introduce them.
- Adding a regex engine.

### Resolution

Implemented in `src/kernel/lua/validate.lua` (`id_problem`, called from `structure`). A bad job id is reported at its key, a bad step id at its value; all are reported. Cases: `validate_bad_job_id`, `validate_bad_step_id`, `run_refuses_bad_id`; unit: `id_length_limit` lives in `src/kernel/lua/validate_test.lua`. Rule added to spec "Workflow YAML" and design §14. `bazel test //...` green.
