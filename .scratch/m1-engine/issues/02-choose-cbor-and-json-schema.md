# 02: Choose the CBOR library and JSON Schema validator

Status: resolved
Type: research
Blocked by: none

## What

Pick one CBOR library and one JSON Schema validator to vendor. Constraints: pure C99 (no C++), permissive license, vendorable, and buildable with Bazel with no code generation. Candidates to evaluate include tinycbor, libcbor and QCBOR for CBOR, and for JSON Schema any C validator, or a Lua validator running on the embedded LuaJIT.

The validator must support the draft that the plugin `with:` schemas will use. That includes `$ref` inside one document, `oneOf` with a discriminator-style `const` (plugin config unions), and `additionalProperties: false`. It must also be able to validate a schema against the metaschema, which ticket 09 needs.

Write the answer, and the reason for it, in this file under `## Answer`. If the decision is hard to reverse, record it as an ADR in `docs/adr/`.

## Answer

Decided 2026-09-19. Full research, with citations and evidence: `.scratch/m1-engine/research/02-cbor-and-json-schema.md`. The architectural consequence is recorded in **ADR-0009**.

| Component | Pin | License | Role |
|---|---|---|---|
| **TinyCBOR** (intel/tinycbor) | tag `v7.0` (`6442e749ca81`) | MIT | CBOR in C: kernel, transcoder, result pipe |
| **`qwe.cbor`** (ours) | — | — | ~300–400-line C Lua module: CBOR ↔ Lua tables over TinyCBOR |
| **lua-schema** (fperrad) | commit `1a14a04c8586ce136d39f8e189f032a460c81ef1` (**not** tag 0.1.2) | MIT | JSON Schema validator, **draft-07**, run on the parent's LuaJIT |
| **LPeg** | 1.1.0 | MIT | lua-schema dependency (`lpeg.utfR` needs ≥ 1.1) |
| **dkjson** | 2.8 | MIT | Parses `schema.json` files |
| compat53 | local ~15-line shim | — | `utf8.len`, `math.tointeger` for lua-schema |

**CBOR in C: TinyCBOR.** It's C99 and never allocates: a cursor walks the buffer, and container offsets stay stable. It can read and write tags. With two small headers normally generated by CMake written by hand, it builds as a plain `cc_library`. Pin the tag: `main` is ahead of it.

**CBOR in Lua: our own C module over TinyCBOR.** The kernel has to convert CBOR to Lua tables anyway to give plugins their `with:` inputs, and forked children inherit the module for encoding results. FFI isn't a good fit, because 59 TinyCBOR functions are `static inline`. The module gives:
- maps and arrays their own metatables, which is what lua-schema needs to tell `[]` from `{}`,
- a `null` sentinel,
- a distinct secret type,
- a depth limit.

It rejects integers larger than 2^53, because LuaJIT numbers are doubles.

**JSON Schema: lua-schema, draft-07, validated in Lua.** No usable C validator exists (see the rejected candidates below). lua-schema runs on LuaJIT and reports each error as a JSON Pointer into the data (`/jobs/build/steps/1/with/pth`), which the transcoder's position table maps to `file:line:col`. That means the position table is **keyed by JSON Pointer and records key positions as well as value positions**, which ticket 04 must provide. Draft-07 was chosen over 2020-12 because draft-07's metaschema reuses itself at every level (`{"$ref":"#"}`), which makes the strict metaschema below a one-line change.

**Catching `"requried"`: the qwe strict metaschema.** Standard metaschemas accept unknown keywords. qwe uses its own copy of the draft-07 metaschema with:
- a qwe `$id`,
- `"additionalProperties": false` at the root, which applies at every level,
- `pattern`, `patternProperties` and `format` **removed**,
- qwe's own keywords added (`secret` for output schemas),
- `$schema` pinned to draft-07.

`qwe validate` checks every schema against it before compiling the schema.

**`pattern`: not supported in M1.** A schema that uses it is rejected by the strict metaschema, so it's never silently ignored. When a plugin needs regex matching, add PCRE2 10.48 (BSD-3 with the PCRE2 exception, ships its own Bazel BUILD) through lua-schema's custom keyword hook, and document which regex dialect qwe accepts.

**Plugin unions use `if`/`then`, not `oneOf`.** lua-schema reports the errors of every `oneOf` branch mixed together. The kernel composes the step schema as `allOf` of `if: {properties: {uses: {const: X}}} then: {$ref: X}` per plugin, plus `uses: {enum: [...]}`, so errors come only from the matching branch.

### Rejected

- **QCBOR** (BSD-3, strict C99, no malloc) is the runner-up and the drop-in fallback. It lost because:
  - nesting is capped at 15 at compile time (a workflow already uses about 6 levels before `with:`),
  - the encoder moves earlier bytes when it closes a container, which breaks positions keyed by byte offset,
  - its decoder is stateful and awkward to backtrack.
- **libcbor** (MIT) allocates a reference-counted tree per item, and its Bazel support shells out to CMake. It has no advantage over TinyCBOR's cursor.
- **NanoCBOR** (CC0) needs GNU C extensions (gnu99, anonymous unions, `htobe64`), has no tagged releases, and is tuned for known structures on microcontrollers.
- **cn-cbor**: dormant since 2020, including its fork.
- **zcbor**: validation means generating Python code from CDDL, which the design's no-codegen rule forbids.
- **lua-cbor (Zash)**:
  - encodes every Lua string, including map keys, as a byte string,
  - has a fallback float-decoding bug on LuaJIT (`2^-768` decodes as `inf`, tested),
  - its source is only available through hg or a rock.
- **org.conman.cbor**: LGPL-3.0+, disqualified.
- **lua-ConciseSerialization** (MIT) is good, but silently drops unknown tags. It's the pure-Lua fallback if ever needed.
- **api7/jsonschema**:
  - errors are one prose string with no usable instance pointer, and a failed `oneOf` says only "matches none",
  - it needs PCRE1 through lrexlib and net-url,
  - it reads the `ngx` global, which conflicts with strict globals,
  - it has no metaschema check.
- **ljsonschema / lua-resty-ljsonschema**: draft-04 only (no `const`), prose errors, and the original has been abandoned since 2019.
- **WJElement**: draft 3 with partial draft 4, no `const`, a contradictory license (MIT vs LGPL vs AGPL), and no release since 2017.
- **jsonc-daccord**, the best pure-C option:
  - needs json-c, so a CBOR→json-c conversion plus json-c's CMake-generated headers,
  - has no metaschema validation,
  - reports errors by schema keyword rather than instance pointer,
  - its `pattern` uses POSIX ERE.
- **jsonschema-c**: draft 4, autotools, abandoned since 2016.
- **The C++ validators** (valijson, pboettch/json-schema-validator): ruled out by the no-C++ rule.
- **Writing our own C validator**: about 2–3k lines reimplementing `$ref`, output formats and the metaschema check, for no gain over the Lua route, which needs the CBOR→Lua conversion anyway.
- **CDDL** (RFC 8610) instead of JSON Schema: no decisive advantage, and it has no runtime C validator we could verify. We stay on JSON Schema.

### Follow-ups this creates

- **Ticket 03:** vendor TinyCBOR, and add the in-repo round-trip test (moved from this ticket).
- **Ticket 04:** the position table must be keyed by JSON Pointer and include key positions.
- **Ticket 05 / ticket 09:**
  - vendor lua-schema, LPeg and dkjson,
  - write the strict metaschema,
  - compose the step schema with `if`/`then`,
  - run the upstream JSON-Schema-Test-Suite (draft-07) as a Bazel test to guard against a beta, single-maintainer dependency.
- **Ticket 15:**
  - Decide how a secret-typed value satisfies `type: string` in a `with:` schema (for example a custom keyword or a placeholder string substituted before validation).
  - Choose the secret tag number from RFC 8949's first-come-first-served range (≥ 32768), defined in one header shared by C and Lua.
- **Still open:**
  - positions for errors inside `schema.json` files (dkjson gives none; options are listed in research §6.4),
  - whether dkjson works under strict globals (not verified; load third-party Lua in its own environment).
