# A plugin file has no top-level code, and validation reads it rather than running it

`qwe validate` decides a project plugin's contract from its **source**, executing none of it. `qwe.pluginshape` (`src/kernel/lua/pluginshape.lua`) parses `plugin.lua` with luacheck's parser and allows at the top level only: `local` declarations of inert values (literals, function literals, table constructors, reads, operators, `require` of a module qwe embeds), `M.name = <inert>` assignments — which is what `function M.x()` is — and a final `return` of the module table. A call, a loop, an `if`, a do-block, a rebind or a `require` of another project file is refused with `file:line:col`. The returned table must export `check` and `apply` as function literals or local functions, or `argv` for a run-like plugin, decided the same way. So a plugin file **does nothing when it loads**, and that is checked rather than asked for.

Validation used to load the plugin and call it: `plugincheck.check_lua` ran `loadstring` and then `pcall(strict.run, name, chunk)`, because the contract check needed the module table the chunk returns. That executed a project plugin's top level with the operator's full privileges and no sandbox, during the one command a person reaches for when they do *not* trust a directory (`tests/e2e/validate_runs_plugin_top_level` demonstrated it by writing a file). Three ways out were weighed: accept it and document it; run the top level in an unprivileged child; decide the contract from source. The first attempt at the third was a `kind: "check-apply" | "argv"` field in `schema.json`, with the contract checked when the step ran — **reverted**, because it moved the guarantee that `apply` exists from validate time to run time, where the operator finds out with the hardware already in hand, and it still left the top level running. Analysing the source keeps both guarantees at validate time: the entry points exist, *and* loading the plugin cannot have done anything. Running the top level in a child was heavier than either and was not attempted.

## Consequences

- `qwe validate` executes no project plugin code. It still reads the source, compiles it, and runs luacheck over it — both of those parse rather than run. This does not change the trust boundary (`CONTEXT.md`, "Trust boundary"): `qwe run` still runs a project plugin's `check` and `apply` as the operator, and a workflow can run any command through `run:`.
- A plugin has **no load-time setup**, and no `init` hook is offered — it would be the only place setup could go, which is the point. Work that would have sat at the top level belongs in `check`/`apply`, which run per step in a forked child (ADR-0001), so it is paid per step rather than once.
- The check is deliberately **conservative**: a computed or reassigned export (`M.apply = pick()`) is refused as a call, though it would have produced a function. A plugin author who hits this rewrites the export as a function literal.
- `require` is limited to modules qwe embeds, so a project plugin is a **single file**. Shared code between project plugins has no home yet; it becomes a built-in or it is duplicated.
- Built-in plugins are held to the same shape — `plugins/builtin/lint_test.lua` runs `plugincheck.check` over each one — so the kernel cannot exempt itself and let the rule drift.
- Pinned by `tests/e2e/plugin_top_level_refused` (validate and run both refuse, and the side effect never happens), `tests/e2e/plugin_contract_missing_apply`, and `src/kernel/lua/pluginshape_test.lua` for the accept/refuse table.
